# HiF4 自主迭代流程

## 1. 目标

这套流程不是让 Agent 反复“调一个系数”，而是持续提出可证伪的结构级量化算法，完成实现、审查、评测、复盘和下一轮任务生成。正式比较目标仍是完整 300 例上的综合分，同时保留 Linear MSE、Attention MSE 和运行时间，防止只看到一个总分。

固定边界不参与优化：NVFP4 按 E2M1 数值乘输入 E4M3 scale 反量化，每 16 个连续值共用一个输入 scale，最后恢复原 shape。

## 2. 借鉴了哪些研究经验

本项目没有整体引入某一个框架，而是只吸收适合当前约束的机制。

| 来源 | 可复查资料 | 本项目采用的经验 | 具体落点 |
|---|---|---|---|
| OpenEvolve | [官方仓库（2025）](https://github.com/algorithmicsuperintelligence/openevolve) | 质量与多样性并存、级联评测、完整实验档案 | Pareto 档案；60 例筛选后再跑 300 例 |
| GEPA | [Agrawal 等，2025](https://arxiv.org/abs/2507.19457) | 标量奖励之外还要保留文字反思；从 Pareto 候选提取互补经验 | 下一轮注入带指标的正例、反例和 Take Away |
| PACEvolve | [Yan 等，2026](https://arxiv.org/abs/2601.10657) | 裁剪上下文；停滞时回退并提高探索 | 每类最多保留少量相关记忆；连续无新最优时奖励新算法族和 scratch |
| AdaEvolve | [Cemri 等，2026](https://arxiv.org/abs/2602.20133) | 用累计改进信号动态分配搜索预算 | 算法族历史收益和失败次数进入优先级 |
| PiEvo | [Pu 等，2026](https://arxiv.org/abs/2602.06448) | 不只演化方案，也让研究原则接受异常和反例修正 | 原则可 add/reinforce/challenge，但需跨算法族证据才能激活 |
| EvoScientist | [官方论文（2026）](https://arxiv.org/abs/2603.08127) | 持久保存成功与失败研究经验 | `experiments.json` 同时登记正收益、退化、超时和工作流失败 |
| AutoSOTA | [清华 FIB Lab 官方仓库（2026）](https://github.com/tsinghua-fib-lab/AutoSOTA) | 独立只读验证、防止工作区串扰、可恢复长任务 | 独立快照、哈希边界、全局串行评测和报告阶段 checkpoint |
| EvE | [官方仓库（2026）](https://github.com/scaling-group/eve) | 解题代码与 Agent 指导共同迭代，但指导更新也要评测约束 | 报告生成原则建议，Runner 用证据门禁更新，而非直接改提示 |

这些论文或仓库支持的是流程设计动机，不证明它一定提高本赛题得分。流程是否有效，要看后续单位时间内的有效版本数、重复失败率和正式得分提升。

## 3. 一次任务怎样运行

```text
全局候选池
  ↓ 动态优先级，最多派发 6 个
轻量隔离快照
  ↓
调研 → policy.md → solution.py / trials
  ↓ 写入范围与结构审查
固定 60 例筛选（多配置）
  ↓ 前 2 名
完整 300 例正式评测（全局串行）
  ↓
report.md + 结构化反思
  ↓
版本账本 + 正负记忆 + Pareto + 3 个后续方向
  ↺ 回到全局候选池
```

实现、调研可以并行；大数据数值评测串行。这是因为当前 `linear.pt` 与 `attn.pt` 合计约 3.7 GB，同时启动多个评测进程会放大内存和磁盘抖动。

## 4. 分级评测为什么这样做

一个算法最多有 3 个内部配置。旧流程会让每个配置各自加载一次 3.7 GB 数据并跑满 300 例。新流程分两步：

1. 从 10 个 Linear group 中等距取 2 组，从 50 个 Attention group 中等距取 10 组，得到 10 + 50 个 case；同一进程一次加载数据后连续评所有配置。
2. 按筛选综合分选前 2 名，再在一个进程中跑完整 50 + 250 例。

筛选仍保持 Linear : Attention = 1 : 5，但只有 60 例，因此它的总分量级与 300 例不同。它只能决定同版本配置是否晋级，不能写入 `.agent/versions.json`，也不能作为算法正式收益。

数据使用 PyTorch 的只读内存映射加载。筛选阶段虽然读取同一组 `.pt` 文件，但只在访问被选 group 时触碰对应数据页，不再为每个配置反复完整读入 3.7 GB 文件，也不需要额外保存一份筛选数据集。

如果只有 1～2 个配置，则跳过筛选并直接做完整评测，因为晋级名额本来就是 2，额外筛选无法淘汰任何候选。

## 5. 动态优先级

每个候选不再直接继承来源版本的原始总分。Runner 计算：

```text
priority = 来源质量
         + 证据强度
         + 新颖性
         + 不确定性探索价值
         + 同算法族历史平均收益
         + 少样本算法族探索奖励
         + 停滞时的转向奖励
         - 预计评测成本
         - 同算法族失败惩罚
```

每个分量都保存在任务的 `priority_components` 中，可用 `runner.py status --explain` 查看。证据强度、新颖性和成本是提案者的先验估计，不是实验事实；真正完成后，算法族奖励会由正式结果覆盖先验影响。

派发一批任务时还会先覆盖不同的 `focus`，再覆盖不同算法族，最后才按优先级补满空槽。因此高分来源产生的多个相似提案不会在同一时刻占满全部 6 个 Agent；这个多样性约束只影响并发批次，不改变正式结果排序。

## 6. 为什么维护 Pareto，而不是只留最高分

当前三个初始方法恰好各有不同价值：

- `v0_softmax_aware_qk` 综合分和 Attention MSE 最好；
- `v0_alternating_joint_fit` Linear MSE 最好；
- `v0_hessian_repair` 在当前记录中运行时间最短。

若只保留综合最高分，Linear 新策略可能丢掉更合适的实现基础，速度优化也没有起点。因此 `.agent/knowledge/pareto.json` 同时把得分视为越大越好，把两类 MSE 和耗时视为越小越好，保存没有被另一版本全面压过的版本。正式全局冠军仍按综合分决定，Pareto 只负责保留有用多样性。

## 7. 研究记忆如何避免越积越乱

`experiments.json` 保存每个版本的基线、分数差、两类 MSE 差、耗时、假设判定和 Take Away。给新 Agent 时不复制全部历史，只选择：

- 与当前 focus 最相关的最多 4 个正收益实验；
- 最多 4 个退化、失败或超时实验；
- 当前 Pareto 前沿；
- 活跃研究原则和连续停滞次数。

这样既能利用失败经验，又不会让几十轮历史淹没当前问题。所有历史经验都只代表本地数据证据，不能当作隐藏集规律。

## 8. 防篡改和恢复

Runner 对以下内容建立一次任务内的哈希边界：调度器、配置、worker/reviewer schema、评测器、评分公式和数据清单。实现 Agent 只能改自己的版本目录；Reviewer 不能改任何文件；评测器也不能改候选 `solution.py`。

快照不含 `datasets/` 与 `reference/`，正式评测只由根目录 Runner 执行。普通 `doctor` 校验数据文件大小；`doctor --deep` 才读取约 3.7 GB 文件并比对 SHA-256。

如果完整评测已经结束，但报告 Agent 或登记阶段失败，Runner 保存的 checkpoint 可在 `recover` 后从报告阶段继续，避免重新运行正式评测。环境启动失败、评测超时、工作流失败和算法失败使用不同状态，避免把 `[WinError 2]` 一类基础设施问题写成算法退化。

## 9. 目前仍需用真实运行验证的假设

- 60 例筛选能否稳定选出完整 300 例中的最佳内部配置；需要统计后续版本的筛选排名与正式排名一致率。
- 动态优先级是否提高单位评测小时的最好分增量；需要与旧静态优先级历史对照。
- 原则记忆是否减少重复失败；至少积累多个算法族后，再比较重复提案率与失败类型。
- 多指标 Pareto 是否真正产生更好的交叉起点；需要记录后续版本从哪个专项版本获得收益。

这些项目应作为流程自身的评测指标，不能仅凭设计合理就判定有效。

`python .agent/runner.py audit` 会持续汇总正收益率、新全局最优次数、筛选冠军与正式冠军一致率、连续停滞长度、失败类型，以及每个正式评测小时获得的正向分数增量。在还没有新分级实验时，筛选一致率会明确显示为 `insufficient_data`，而不是用零或猜测补齐。
