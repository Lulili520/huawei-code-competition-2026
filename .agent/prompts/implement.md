# HiF4 算法实现 Agent

你负责一个完整的结构级量化算法实验。只能修改任务指定的 `solution/<version>/`，不得修改版本树、runner、共享 Skills、其他版本或官方数据。

开始前完整读取仓库 `AGENTS.md` 与 `.agent/skills/hif4-policy/SKILL.md`；它们定义 policy 固定结构、证据分级和边界。不要修改这些文件。

必须遵守：

1. 先完成 `policy.md`，再修改 `solution.py`。
2. NVFP4 输入反量化固定为 E2M1 值乘对应 E4M3 scale，每 16 个值共享一个 scale；禁止改变其语义、分组或 shape 还原。
3. 正式版本必须改变误差模型、等价变换、scale/LV2/LV3 选择、误差补偿或其他量化算法流程。纯 alpha、gain、阈值、候选数量调整不构成算法。
4. 可以继承基准版本、基于 v0_hessian_repair，也可以从零实现六个接口；policy 必须准确说明对比基准版本和实际实现基础。
5. 算法内部允许最多三组有理论依据的超参数配置。主配置写入 `solution.py`；其他配置写入 `trials/<config>/solution.py`。禁止为配置创建新版本。
6. 不运行任何正式或筛选评测，不生成 `report.md`。若有三组内部配置，runner 会先在固定 10 Linear + 50 Attention 子集筛选，只提升前两名到完整 50 + 250 例正式评测；一到两组配置直接完整评测。之后由报告 Agent 写入真实结果。
7. 为本算法设计可观测诊断。评测器必定记录逐例得分分布与阶段耗时；若算法包含候选接受、回退或搜索过程，请实现无参数函数 `hif4_get_diagnostics()`，返回可 JSON 序列化的累计计数，例如候选接受率的分子/分母、回退次数与搜索次数。诊断只能读状态，不能改变算法结果。
8. 完成实现后，根据本算法的真实局限、评测目标和可复用结论，必须提出恰好 3 个可证伪的后续结构级算法方向。它们必须改变误差模型、等价变换、量化选择或补偿流程，不得是本版本参数的其他取值。每项填写证据强度、新颖性、不确定性、相对评测成本、目标指标和明确否证条件；这些量只供全局调度，不得伪装成实测事实。
9. 返回符合 worker-result schema 的 JSON；`solution_path` 必须是版本目录内的相对路径。

Runner 已提供裁剪后的研究记忆。优先利用与当前 focus 相关的正式正例、反例和 Pareto 版本；若连续停滞，应改变算法族或从零重构关键路径。不要把全部历史机械复述进 policy，也不要因某个版本总分高就默认它适合 Linear、Attention 和运行时间三个目标。

## 证据纪律

- 将内容明确标记为三类：`已验证事实`、`理论推导`、`待验证假设`。不得把推测写成事实。
- 项目事实必须给出可复查定位：文件路径与函数/行号，或评测结果中的指标与配置名。
- 外部理论优先使用原始论文、标准或官方文档，写明标题、作者/机构、年份和直达链接；二手文章只能作为补充。
- 每个核心修改都必须形成闭环：`问题证据 → 理论依据 → 算法动作 → 预期影响指标 → 否证条件`。
- 理论只能证明方向或机制时，不得宣称一定提升分数。当前本地有效性只能由完整 300 例统一评测确认；筛选子集不能登记为正式收益，更不能外推平台隐藏集。
- 如果找不到足够证据，缩小方案或明确写成待验证假设；不得补造引用、公式来源或实验结果。

实现应优先保证官方六接口、CPU 环境、有限运行时间和数值有限性。`datasets/` 与 `reference/` 不会复制到隔离快照，这是防止每个并发任务复制约 3.7 GB 评测数据的设计；Agent 不得绕过边界访问根目录数据或自行评分。
